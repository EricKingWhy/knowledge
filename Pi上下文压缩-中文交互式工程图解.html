上下文压缩，
压掉的究竟是什么？

从 Pi 的实现出发，拆开 Compaction（上下文压缩）的触发、摘要、近期保留与 Prompt Cache（提示缓存）机制，再把它接到真正的 Agent 长任务系统里。

● 原文机制已核对10 个阅读节点5 个交互实验手机可用 · 离线运行
一句话：Compaction 不等于删记录，也不等于保存状态。它是把旧对话变成结构化摘要，原样保留近期上下文，再重新拼装下一次模型请求。收益是上下文空间；代价是信息损失风险与缓存前缀失效。
事实 01

旧内容被总结

较早轮次进入摘要，而不是每条都原封不动送给模型。

事实 02

近期对话原样保留

Pi 原文所述当时的默认预算是 20K Token，约 5–20 轮。

事实 03

Prompt Cache 会断

旧摘要替换前缀，后方相同 Token 也无法沿用旧缓存。

01 /

一次 Tool Call，为什么会让上下文越来越胖

模型看到的不是“上一次消息”，而是每次请求重新组装的一段上下文。工具结果、模型输出、用户消息会逐渐累积。

来自原文 · 交互演示第 1 步：用户发起任务

固定前缀（系统提示、工具定义）+ 用户输入，组成初始请求。

关键区别：“一次用户轮次”不等于“一次模型请求”。同一轮内模型可以连续发起工具调用，多次携带完整已有上下文。工具返回的长日志特别容易撑大请求。
02 /

什么时候压缩？Pi 不是每条消息压一次

Pi 优先让正常轮次完整执行，减少频繁改写 Prompt 前缀；当快超限时再处理。

原文机制

自动检查时机

通常在一个 Turn（轮次）结束后检查；如果中途收到上下文溢出错误，可能在轮内压缩。

工程解释

为何不每步压缩

高频压缩既增加摘要请求，也频繁使 Prompt Cache 冷启动；还会累计摘要丢失与语义漂移风险。

03 /

动手调一次 Token 预算

将早期历史压缩，保留最近工作。注意：Pi 的“近期保留 20K”是保留区域的 Token 预算，不是摘要一定有 20K，也不是总上下文上限。

04 /

压缩本身，是一次独立的 LLM 请求

重点不是“模型忽然想起要总结”，而是 Agent Harness（智能体运行框架）专门组织一次压缩任务，给摘要模型不同的角色和输入。

INPUT · SELECT OLDER HISTORYPI COMPACTION

 
原文事实
专用的 System Prompt
普通请求的角色是“解决编程问题”，压缩请求的角色变为“整理可供后续接手的上下文”。摘要重点包括目标、进度、关键决策。
原文事实
可以独立选择模型
压缩请求不是带着先前聊天消息继续对话，而是把要压缩的历史序列化为该请求的输入。因此摘要模型可以不同于执行模型。

 
易错点：“不使用现有对话历史作为聊天上下文”不代表“不给摘要模型旧内容”。恰恰相反，待压缩的旧历史必须作为这次独立请求的任务输入提供。





 
05 /
为什么留住近期消息，缓存依然失效？
Prompt Cache 的核心约束是前缀相同。你改了前半段，即使后半段字符一样，它的 KV 缓存也不能直接接在原来的前缀后继续用。

 

 

  
A. 原来的前缀仍可匹配原文缓存机制

  

  
可沿用的缓存范围（示意）旧前缀
额外需要处理的内容仅新增部分

  

 

 

  
压缩之前
systemtoolsold turnsrecent turns
旧的连续 Token 序列，是已经建立缓存的前缀。

  
压缩之后
systemtoolssummaryrecent turns
第一个改变的 Token 发生在摘要替换处；后面的 recent turns 虽相同，前缀却不同。

 

 
精确结论：压缩会破坏旧前缀的缓存复用，不代表此后永远无法缓存。下一次请求建立新前缀后，后续追加式请求又可以继续受益。





 
06 /
四件事别混：压缩、长期记忆、Checkpoint、Event Log
这是把文章迁移到生产 Agent 系统最关键的一步。它们的读写对象、恢复粒度、故障模型都不同。

 

  
① 原文讨论
Compaction · 上下文压缩
对象：下次模型请求里的消息上下文。
目的：让模型还能继续看得下去。
盲区：摘要有损；不是执行进度快照。

  
② 工程扩展
Long-term Memory · 长期记忆
对象：可跨会话检索的事实、偏好、经验。
目的：按任务需要召回相关知识。
盲区：无法天然恢复控制流。

  
③ 工程扩展
Checkpoint · 状态快照
对象：Graph State、待执行节点、运行状态。
目的：在已记录的安全恢复点继续。
盲区：外部操作是否成功需单独核验。

  
④ 工程扩展
Event Log · 事件日志
对象：按时间追加的输入、工具调用、结果、状态变更。
目的：审计、重建、可验证的回放依据。
盲区：记录事件 ≠ 副作用可以安全重演。

 

 
工程事实：这几个需求分别找谁？

 
“模型聊天太久，快超过上下文窗口”
用 Compaction／裁剪工具结果／按需检索。缩短传给模型的上下文。不要只靠无限扩上下文。

 
“服务重启后，任务要从上一个阶段接着做”
用 Checkpoint 存储状态与节点进度，再通过检查点恢复。摘要只能帮助模型理解之前做了什么，不能单独保证控制流续跑。

 
“同一个工具调用恢复后绝不能重复扣款 / 发消息”
工具侧需要幂等键（Idempotency Key）、操作状态查询、执行账本和回放策略。Event Log 可提供证据，但不能替代外部系统幂等。

 
“Agent 下周要记住用户稳定偏好”
用持久化记忆层（带 scope、版本、冲突处理、检索）。不要指望一份会话压缩摘要自动成为可信长期记忆。

落到多 Agent 系统：不是照抄 20K，而是分层控预算
下面是工程设计建议，不是 Pi 官方实现。例如一个 6 Agent 调研工作流若整次模型调用预算只有 12K Token，就不可能把“Pi 保留 20K”原封不动搬过来。

 
Context Manager每次请求组装、Token 预算
→
Compactor旧历史摘要、近期保留
→
LLM Agent执行下一步

 
Checkpoint Store阶段状态 / JSONB
↔
Evidence Store证据 ID 与可追溯来源
↔
Event & Trace审计日志、工具回放依据

 
预算先算清：12K 总预算与 10K 触发阈值只能是你系统自己的设计参数；先给 System/Tools、输出预留、近期任务、摘要划分空间，再决定裁剪哪部分。不同 Agent 应按职责隔离压缩范围。

 
压缩摘要必须保留什么？

 

  
Goal用户最终目标、交付标准、当前子问题；避免摘要只记过程，不记要解决的问题

  
Progress已完成步骤、未完成步骤、当前阻塞、下一步动作；尽量结构化、可判定

  
Decisions已经拍板的技术选型、被否定的方案、不可违反的约束；防止恢复后推倒重来

  
Evidence IDs引用证据标识、数据版本、路径和原始出处；摘要不能篡改原始工具事实

  
Side effects哪些操作已执行、工具返回的 operation_id、重试风险；不凭摘要判断副作用成功

 

 
一份可改的 Compaction Prompt 骨架

 
你是 Agent 的上下文交接整理器，不是任务执行器。
输入：需要压缩的旧会话与工具结果（已序列化）。
目标：为下一阶段保留可恢复的语义上下文，而不是复述聊天记录。

请按以下结构输出：
1. GOAL：目标、验收标准、边界条件
2. PROGRESS：已完成 / 未完成 / 当前阻塞
3. DECISIONS：确定的方案、拒绝过的方案及理由
4. EVIDENCE：证据 ID、来源、尚待验证的结论
5. NEXT_ACTION：可执行的下一步，包含前置条件
6. RISKS：无法确认、潜在副作用、权限与安全边界

硬约束：
- 不捏造未发生的工具结果，不把猜测写成已验证事实。
- 不生成替代原始证据的虚构引用。
- 对不确定信息显式标记 UNKNOWN。
- 仅保留与当前目标持续相关的上下文。
- 输出紧凑，优先保留决策、阻塞与证据定位符。

 

  
建议 · 质量门槛
摘要完成后，做一次校验
检查目标、当前阶段、待办、关键决策、证据 ID 是否被保留；抽查与原始事件记录有无矛盾。错误摘要会持续污染后续轮次。

  
建议 · 成本门槛
不要只盯摘要 Token 数
同时测压缩请求成本、首次缓存冷启动、后续稳定缓存命中，以及压缩后任务成功率。最短摘要不一定最优。

 

 
失败模式 → 对应控制点

 
摘要遗漏重要约束
将权限、核心决策放结构化状态；关键字段必填并校验，不全时拒绝替换。
工具结果占满窗口
从源头限制大结果；保留摘要与引用句柄，详细内容按需读取。
压缩后 Agent 重复执行
恢复运行依赖状态机 + 幂等键 + 外部执行结果核对，而不是摘要文字。
频繁压缩使缓存抖动
按轮次边界进行压缩，监测压缩间隔、首请求 miss 和单位成功任务成本。

三道题，检验是否真的理解
不是背概念，选工程上最准确的解释。点击选项立即看判定。

 
Q1. Pi 保留“最近 20K Token”意味着什么？

 
Q2. 压缩后最近 20K 消息完全相同，为什么旧 Prompt Cache 仍可能失效？

 
Q3. Agent 压缩并恢复后再次发送一笔付款，最缺少的保障是什么？

 
面试式总结：Pi 的上下文压缩由 Harness 管理，轮次边界优先触发；它把旧历史交给独立摘要请求，保留一段近期原始消息，再拼装新上下文。代价是有损摘要和缓存前缀重建。生产长任务还需要独立的 Checkpoint、事件记录和副作用幂等。
