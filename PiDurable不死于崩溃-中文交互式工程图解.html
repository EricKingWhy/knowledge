DURABLE AGENTS / 从会聊天到能续跑

Agent 不应该
死于一次崩溃。

Pi Durable 把对话、模型调用、工具执行和应用状态统一放进持久化任务状态机。进程消失后，另一进程打开同一份存储，就能沿着已提交的执行状态继续。

主题 Pi Durable依据 官方 README / 作者文章难度 进阶入门形式 交互式单页
一针见血： 普通会话恢复解决“历史消息还在不在”；Durable Execution（持久化执行）解决“任务进行到哪一步、哪些副作用可能已发生、重启后哪些动作能继续”。
这不是“让 LLM 记性更好”，而是让 Agent 的控制面具备可恢复性。
01 / THE PROBLEM

真正的故障，不是丢了聊天记录

假设 DeepResearch 已搜完 40 个页面、写好阶段分析，正调用工具写报告。此时进程 OOM。你可以重新读取聊天记录，但这不代表能安全地从上一个步骤继续。

RECOVER 01

Transcript（会话记录）

保存用户消息、模型回复与工具输出。解决“之前聊了什么”，不保证在途工具被追踪。

RECOVER 02

Checkpoint（状态检查点）

保存当前阶段、计划、局部状态和执行指针。解决“从哪一步继续”，但不自动处理外部写操作。

RECOVER 03

Durable Runtime（持久运行时）

将提交、任务调度、调用意图、恢复策略、因果所有权联成一套约束，而非几张数据库表。

能力边界：恢复执行 ≠ 不中断运行。Pi Durable 需要进程重新启动并重新打开存储；它并不承诺进程退出后计算仍在后台继续。
02 / MENTAL MODEL

先有可提交的“事实”，再执行下一步

关键设计叫 Intent Before Effect（意图先于副作用）：先在本地持久化“我要执行哪个工具”，再真的去调用。这样崩溃时至少知道那个动作曾被发起。

① Input
用户输入 / 唯一 requestId
›
② Commit
记录任务、意图与阶段
›
③ Execute
LLM / 工具 / 子任务
›
④ Commit
结果、状态、后续任务

不可变 Entries（事件条目）

用户输入、模型回应、工具结果、系统提示变更等，以追加方式形成可追溯记录。它们承载对话与证据，但不等于执行控制的全部。

Documents + Tasks（文档与任务）

Documents 是类型化 JSON 状态；Task 是带阶段与 checkpoint 的持久化状态机。同一次 Commit 可原子地提交记录、状态变更和新任务。

事务边界必须看清：数据库 Commit 能保证本地状态的原子性；不能自动把外部 HTTP、支付、邮件与本地数据库合并成分布式事务。
最小恢复路径 / TypeScript（依据官方 API 精简）
import { Harness } from "@earendil-works/pi-durable";
import { openNodeSqliteStorage } from
  "@earendil-works/pi-durable/storage/sqlite/node";

const storage = await openNodeSqliteStorage("./session.sqlite");
const harness = await Harness.open(storage, { models, registry }, context);
const root = await harness.root(context);
harness.resume();    // 重新调度已保存但未完成的任务

注意：这是集成片段，models、registry、context 需要由宿主创建。选择 MemoryStorage 不会获得跨进程恢复能力。

    04 / TASK OWNERSHIP

    并发任务，必须知道“谁对谁负责”

    Pi Durable 将 Task Ownership（任务所有权）变成运行时结构。父任务可以创建子任务并等待；失败、取消与收尾有明确传播规则，不再依赖模型“记住谁该停”。

    子任务并发调度实验

    3 个并发子任务
    Supervisor / Research Task
    owner → children · checkpoint = waiting
    ⌕Search A等待
    ⌕Search B等待
    ⌕Search C等待
    allSettled：父任务等三个子任务都进入终态，再汇总成功与失败结果；适合尽可能收集证据的研究任务。

    allSettled

    不因一个子任务失败就放弃其他可用结果。适合多路搜索、独立证据收集、并行评测，代价是要处理部分失败。

    failFast + Bottom-up abort

    一项失败可触发同组其余任务中止；父任务取消时先处理它拥有的子任务，再执行自己的清理逻辑。适合强依赖型工作流。

    注意：background: true 可形成所有权边界，不意味着所有子任务都会随父任务终止。“不会残留任何孤儿进程”不能无条件保证；外部系统进程需要单独的生命周期管理。

    05 / CLAIM AUDIT

    原帖哪些准确，哪些要加限定条件？

    热帖适合建立直觉，工程实现必须回到官方文档。下面给出明确的事实边界。

    流行说法准确解释工程判断
    “先写 WAL，再执行”关键保证是持久化意图与原子 Commit。SQLite 后端使用 WAL；JSONL、Cloudflare SQLite 等后端实现不同。原则成立
    “重启从原地继续”重开同一存储后，任务按最近 checkpoint 恢复；中断的模型请求可能重新发送，带来额外成本。有条件成立
    “只有安全工具重跑”工具必须显式声明 replay: "safe"。非安全工具恢复时返回 interrupted，不是自动保证外部世界无变化。关键边界
    “崩溃最多丢 100ms”默认约 100ms 是部分文本/工具输出的提交频率，不是停电下全部持久性承诺；存储设置也会影响。常见误读
    “子任务失败绝不残留”Task Tree 有任务所有权与自底向上 abort；但后台任务边界、外部进程和无法取消的远程调用另算。不能绝对化
    “可用于生产”有成熟的执行模型，但包仍标为 Experimental、API 可能变动，宿主仍负责权限、安全、外部幂等与运维。需评估
    额外细节：官方 SQLite 默认采用 WAL + synchronous=NORMAL；这一般可以在进程崩溃后恢复已提交状态，但主机断电时最近的提交仍有风险。不要把“进程崩溃可恢复”等同于“任意硬件故障零丢失”。
    06 / ENGINEERING BLUEPRINT

    放进你的 Agent 项目，怎么做才不重？

    Pi Durable 当前是 TypeScript 生态的运行时。对 Python / LangGraph / PostgreSQL 架构，更合理的是借鉴它的执行语义，而不是为了一个包重写整套服务。

    TARGET ARCHITECTURE

    DeepResearch：阶段恢复 + 副作用冻结

    把 6 Agent 的研究阶段保存为 Checkpoint；工具执行用 operation_id 绑定意图、结果和版本，恢复时先复用已完成结果。

    落地门禁

    独立于框架的伪代码 / Python 思路（非 Pi API）
    # 不在未知结果上盲重试写操作
intent = db.create_or_get_intent(operation_id, payload)
if intent.status == "done":
    return intent.result

if intent.status in ("running", "unknown"):
    remote = provider.lookup(operation_id)  # 查询外部事实
    if remote.confirmed:
        return db.mark_done(operation_id, remote.result)
    if remote.uncertain:
        raise NeedsReconciliation(operation_id)

# 外部接口也须支持幂等键；状态机防重只是其中一层
result = provider.execute(payload, idempotency_key=operation_id)
db.mark_done(operation_id, result)
return result
    部署现实：两种恢复边界不能混淆：单进程本地 SQLite 适合轻量 Agent；多 Worker 共享同一任务队列时，还需要租约/排他执行、故障接管和状态一致性。Pi Durable 官方目前约束同一存储一次由一个进程拥有，不能直接拿它充当多实例共享调度器。
    07 / CONCEPTS

    Checkpoint、Event Log、Replay、Durability 怎么区分？

    机制解决的问题不保证的事情
    Conversation Resume恢复会话身份与可见历史不能推出在途工具状态
    Checkpoint保存阶段状态与执行位置不自动保证外部副作用幂等
    Event Log记录先后发生的输入、输出、状态变动日志本身不负责调度、恢复策略
    Replay通过已存记录重建观察状态或重演安全步骤不应该无条件重新执行写操作
    Durable Runtime把提交、调度、任务所有权、恢复政策做成执行约束不解决跨系统恰好一次与所有运维问题
    DON'T

    错误恢复逻辑

    if not result: tool.execute()

    没有结果可能是“没执行”，也可能是“执行成功但结果丢了”。对于写操作，这个分支极危险。

    DO

    正确的恢复顺序

    inspect → reconcile → replay / resume

    先读任务状态，再查询外部事实，确认安全边界后才决定重试、跳过或人工介入。
