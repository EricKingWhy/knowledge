01 / POSITION

核心不是 Skill 多，而是决策质量高

模型能力越强，越应该区分「明确的工程约束」和「复杂但没有增量价值的仪式」。过重的 Harness（运行支撑体系）会多耗 Token、增加噪声、制造不必要的交接点。

低效路径

工具先行

为新增一个 RAG Reranker，先让 6 个 Agent 开会、生成长篇 Spec、重复 Review 三轮，最后没有任何离线评测。

问题：流程数量代替了质量证据。
推荐路径

证据先行

先定义 NDCG / Recall / p95 延迟和线上可接受成本，做局部实现、固定样本回归，再决定是否保留改动。

收益：迭代结论可以被复验。
有条件的例外

高风险需加闸门

OnCall 涉及自动重启、告警抑制、工单写入时，要有审批、幂等、回放和权限验证；不能为了省流程去省安全。

原则：复杂度由风险触发，而非习惯触发。
一针见血：一个工作流存在的唯一理由，是它减少了某种可观察的失败：需求偏差、实现缺陷、回归事故、不可恢复状态或错误权限。否则删掉。

DeepResearch

复杂并不等于有效

6 个角色齐全，不代表 6 个角色都给质量带来了增益。把「规划、搜索、分析、代码、写作、审核」拆成可测量的边际贡献。

OnCall

简单不等于安全

自动重启只需一次工具调用，但必须能判断重试是否重复执行、命令是否可逆、状态是否可能不一致。

04 / ABLATION LAB

交互消融：到底哪个模块在发挥作用？

消融实验（Ablation Study）：从完整系统拿掉一个模块，在相同测试集、模型、版本和参数条件下比较变化。这里采用 演示数据 来说明分析方法，不能当作你的项目实测结果。

保留哪些组件？

选择启用或移除，再看模拟结果。实际消融时应逐项变化，不能把多个模块同时删掉后归因给单个模块。

数值是教学用的假设示例：相互作用可能存在，不要把这些变化理解为准确预测。

演示指标

怎么让消融可信？

  1. 冻结数据版本、评测集与基线 Prompt。
  2. 一次只改变一个组件；记录每个配置与种子。
  3. 同时看质量、成本、延迟和失败类型。
  4. 对高方差任务做重复运行并给出置信区间。

删掉模块的决策规则

不是「F1 涨了就留」。对 Agent 更实用的是：质量增益是否稳定、是否压过复杂度、是否触碰风险阈值。

例如一个搜索扩展 Agent 让证据覆盖率提高 2 个百分点，却令延迟翻倍、引用错误率上升，就不一定值得保留。

06 / PROVE IT

Code Review ≠ Runtime Verification

两个 Gate 的职责不可互相替代。AI 写完代码、自称测试通过，不构成交付证据。这里模拟如何审查 Agent 的真实行为，而不是只看代码风格。

Review · 静态证据

查设计与代码缺陷

  • 工具权限是否与意图一致？Tool Registry 是否做白名单？
  • 并发 Tool Call 是否绑定正确 tool_call_id？
  • 副作用操作是否有 operation_id 与幂等协议？
  • RAG 的证据映射是否可追溯到 chunk_id？
  • 新增抽象是否有真实复用需求，还是预设计？
Runtime · 动态证据

运行真实功能

  • 启动 API，提交请求，确认 SSE 按预期流式返回。
  • 故意让检索工具超时，检查降级与最终状态。
  • 在 Checkpoint 后重启服务，确认不会丢失任务阶段。
  • 模拟写工具「已成功但回包丢失」，验证幂等对账。
  • 冻结 Tool Result 重放，验证终止条件可复现。
