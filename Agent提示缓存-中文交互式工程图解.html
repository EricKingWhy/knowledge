01 / THE MECHANISM

缓存的不是答案，而是计算状态

模型第一次读取输入时的 Prefill（预填充）会生成注意力层的 Key / Value 张量。下一轮的开头若完全相同，系统才有机会绕过对应部分的重复 Prefill。

REQUEST
输入 100K TokenSystem · Tools · History
→
PREFILL
计算每层 K/V每段前缀对应计算状态
→
DECODE
生成新 Token下一轮仍须计算新增部分
WHAT IT SAVES

复用前缀的 Prefill

缓存命中能减少重复处理旧输入的工作量，通常改善成本和首 Token 延迟；生成新回答仍需要 Decode。

WHAT IT DOES NOT SAVE

不等于长期记忆

KV Cache 是服务端、模型相关的计算状态；不等于向量库，不增加上下文窗口，也不能替代 Checkpoint。

严格前提：前缀一致 ≠ 一定命中。即使输入 Token 序列没变，服务端仍可能因 TTL 过期、缓存淘汰或路由变化而无法复用。正确理解是“具有复用资格”，不是“保证命中”。

缓存通常存在哪里？

A · SESSION AFFINITY

会话亲和路由

把同一会话尽量调回已有 KV 的 GPU / Worker。速度快，但容易受机器重启、负载均衡、淘汰影响。

B · DISTRIBUTED KV

分布式 KV 块

多个 Worker 可访问共享缓存块。调度灵活，但需要解决 KV 块索引、迁移、存储、淘汰及一致性相关问题。

原文事实 两类是推理基础设施的实现策略，不能仅通过本地 Agent 的 session_id 强制服务商保留 KV。

03 / API CONTRACTS

两种缓存策略，和一个工具陷阱

缓存机制由推理 API 实现，Agent 能控制的是输入稳定性、断点和路由提示。它无法凭缓存 Key 强行让不一致的内容命中。

EXPLICIT CACHE

显式 Cache Breakpoint

Anthropic 支持 `cache_control`：指定“前面的这段是稳定前缀”。仍要求内容精确匹配，并受可缓存长度、TTL、模型等限制。

AUTOMATIC CACHE

自动前缀匹配

由服务商尝试识别可复用的前缀。`prompt_cache_key` 或 session hint 主要帮助分组/路由，不能修复前缀变化。

Anthropic API · 结构示意，不是可直接执行的完整请求

  "system": [{
    "type": "text",
    "text": "稳定的角色与全局约束",
    "cache_control": { "type": "ephemeral" }
  }],

工具 Schema：最容易被忽视的前缀污染源

❌ CHURN

每轮重写 Tools

工具增删、参数 Schema 变化、工具排序漂移，会改变位于对话前面的输入。只省几百个 Schema Token，却可能使后面 80K 历史重新计算。

✓ ADDITIVE

支持时：锚定位置增量加载

在有原生延迟工具机制的模型上，新增工具可在后续消息位置生效，保留旧前缀。Pi 可对纯增量变更使用此能力；不支持则回退为完整工具列表。

落地抓手：工具 Registry（工具注册表）保持稳定排序、稳定参数序列化；把时间戳、Trace ID、变化的 RAG 检索结果放到适当的动态位置；模型原生支持时再使用延迟加载。不要把“按需加载工具”简单等同于“节省费用”。
04 / CACHE LIFETIME

会话没断，不等于缓存还在

Anthropic 常规 Prompt Cache 默认约 5 分钟，可选 1 小时缓存时长（写入价格更高）。计时基于写入或读取请求开始的时刻，不是从输出结束才开始。

06 / THE BREAK-EVEN

什么时候删历史才真的划算？

删除中间消息会破坏之后所有旧内容的匹配。一次性重算成本，必须由后续反复少传的 Token 省下来；这还没算质量损失。

Pruning（剪枝）回本计算器先不计新的缓存写入溢价，因此倾向于低估重写成本
至少还需要多少次“同样可命中”的后续请求才能回本126 轮
↗
粗略推导 · 相同 Token 单位
一次重算净代价 ≈ 编辑点后保留 Token × (普通价 − 读价)
每轮少传收益 ≈ 删除 Token × 读价
回本轮数 ≈ 一次重算净代价 ÷ 每轮少传收益
注意两条额外约束。 (1) 上下文接近窗口上限时，压缩可能是必要条件，而不是成本最优选择；(2) 工具结果里可能存着先前决策的证据，删除会影响正确性，不能仅用 Token ROI 判断。原文方向 Pi 选择相对稳定、追加式的记录；当上下文压力大时再 Compaction（上下文压缩）。
07 / SYSTEM DESIGN

落到真正的 Agent：我会怎么改

下面属于工程延伸，不是原文声称 Pi 已实现的全部功能。可以直接映射到 LangGraph、RAG 和长任务 Agent 的请求组装与观测层。

① Stable Prefix Builder固定 System、工具顺序、JSON Schema、版本；对稳定部分计算 fingerprint
② Dynamic Suffix Builder把当前 query、检索证据、Trace ID、阶段结果追加到后部
③ Cache Telemetry分开统计 cache read / create / uncached；定位首次失配与 TTL 空闲
场景切换 · 工程决策按你的实际项目类型看不同优化重点

Checkpoint、Compaction、Prompt Cache 必须分层

能力核心作用处理的对象能否跨模型保证恢复
Prompt Cache少做重复 Prefill模型 / 推理服务端 KV 状态不能保证
Compaction挪出上下文窗口输入历史的摘要/重写新模型可读摘要，但会重建缓存
Checkpoint崩溃后恢复流程节点图执行状态、任务进度、指针取决于状态序列化/兼容性
Event Log审计与回放追加事件、参数、结果、时间线可供回放，但需控制副作用
一句话架构规则：Cache 提速，Compaction 控窗，Checkpoint 续跑，Event Log 留证。 别把这四层合并成一个“长期记忆模块”。
08 / OBSERVABILITY

缓存命中率突然掉了，查什么？

没有可观测性，就只能在账单上猜问题。Pi 的状态栏会显示 R/W/CH，`/session` 可以检查累计缓存和重复计费估算；一般 Agent 也应该做到。

01空闲超过 TTL

检查前后两次 API request-start 间隔，而不是会话是否打开。

02切换模型 / 网关

检查 provider、model、路由 Key；不同模型 KV 通常不可搬用。

03工具定义漂移

对 tools 名称、排序、Schema 序列化做稳定指纹比对。

04动态 System Prompt

检查时间戳、随机内容、扩展插件是否在前面修改消息。

05会话分支 / Rewind

同 session_id 不代表同 token 前缀，检查 active branch。

06手动剪枝 / Compaction

这是预期的缓存重置；区分计划性重置与异常未命中。

07Extension Transform

本地历史未变，但出站请求载荷已被插件二次改写。

08服务端路由 / 淘汰

前缀哈希一致但读缓存很少时，注意服务端不可见边界。

09 / QUICK CHECK

三道题，确认你理解的是机制

不考定义，考设计决策。点击答案直接显示解释。

最终结论：保持稳定前缀，避免不必要的工具/系统提示变化；用实际的缓存读取、缓存写入和未缓存费用做观测；在上下文窗口、任务质量或长期收益需要时，再有意识地重写历史。比“少发 Token”更好的优化目标：每次完成有效任务的总成本与延迟。
