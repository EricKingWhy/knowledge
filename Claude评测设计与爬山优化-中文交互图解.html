01 THE BIG PICTURE

先建立尺子，再决定怎么爬坡。

这篇文章讨论的不是「让模型多试几次」那么简单。关键在于用一个贴近生产、足够稳定的评测体系，为每次改动提供可信的反馈；并始终保留一组优化器看不到的案例，识别过拟合。

PHASE 01
构建 Eval

选取真实任务 → 校准评分器 → 跑基线 → 估计噪声

→
PHASE 02
逐轮 Hillclimb

分析训练失败 → 一次改一个点 → 重新评测

→
PHASE 03
留出集把关

看未见过的案例是否同步提升；否则回滚

一句话理解：Eval 是用来测量的尺子，Hillclimb 是沿着坡面尝试前进的方法，Held-out Test（留出测试集）则是防止 Agent 对着答案作弊的保险。
02 EVAL DESIGN

评测的四条硬标准。

评测集不是「题越多越好」，而是样本来源、难度区间、打分规则、执行环境四件事要同时可信。原文重点强调如下四点。

01 / PRODUCTION ALIGNMENT

像生产环境

任务分布应代表真实业务。不要只因为题目容易自动生成、方便评分，就让它占据评测集。

02 / CAPABILITY MONOTONICITY

强模型应普遍更好

更强模型或更高推理投入通常应表现更好；若反常，先检查任务歧义和评分器是否误判。

03 / MEANINGFUL HEADROOM

要有可提升空间

最强配置不能轻松接近满分，但错题也不能是根本做不到、或者专家意见不一致的题。

04 / LOW VARIANCE

重复运行要稳定

同一输出不应被评分器随机判成相反结果；配置、超时、遗留文件或 Git 状态也可能污染评测。

难例采样：为什么不能只收集当前模型做错的题？示意图 · 非原文图

仅挑选某个模型失败的地方，测到的可能只是这个模型的「失败指纹」。应加入 人类预先判断困难 的任务、真实线上故障、Bug 单和「不应触发」的反例。

专家一致性检验：如果两位领域专家对同一题的正确答案都难以达成一致，这道题就不适合直接作为确定性评分依据。
03 /CLAUDE-API BUILD-EVAL

把“评测设计”做成一条可审查流水线。

Claude Code 的 /claude-api build-eval 会先与你确认测试输入和评分方式，之后生成可运行的评测资产。以下步骤可以展开查看。

优先顺序：生产对话记录（需先确认留存与敏感数据要求）→ Bug / 工单 → 人工编写 5–10 例 → 基于代码合成。生成后让人逐条审核输入是否代表真实任务。
输出有限且结构化，就优先用规则、Schema 和测试代码；答案开放但有清晰评判标准，再考虑 LLM-as-a-Judge（大模型裁判）。有基线时可以采用打乱顺序的成对比较。
先跑少量题，向人工展示「题目—输出—评分—理由」，让你检查是否有误判。使用与被测模型不同的裁判模型，并对同一输出重复评分，检查一致性。
记录样本数 × 重复次数 × 模型配置，输出得分与置信区间。检查超时、API 错误、截断和环境残留。如果基线已到约 95% 或以上，转向成本、延迟优化可能更有价值。
生成测试用例、评分器、Runner（评测执行器）、每例 JSONL 与完整 Transcript（执行记录），并提供能跳转到原始 Trace（链路记录）的结果页面。原文说明此类附加页面默认本地静态运行、无需联网。

WHY THIS MATTERS

评分器也是被测对象

如果评分规则偏了，Hillclimb 会沿着错误目标越优化越远。

固定输出 → 精确匹配结构要求 → JSON Schema代码正确性 → 测试开放答案 → LLM Judge

原文特别不推荐只给开放式答案打模糊的 1–5 分；更适合拆成可检查的具体断言。

04 /CLAUDE-API HILLCLIMB

每轮只改一个点；没有证据就回滚。

Hillclimbing（爬山式优化）适合提示词、Skill 描述、工具定义、模型选择和推理投入等「修改成本低、能回滚、结果容易归因」的参数。它不是无限制重写整个 Agent。

TRAIN / 允许被分析

训练集：寻找失败根因

优化器可以看训练集的错误轨迹，并据此提出一项通用修改，例如纠正冲突的路由规则，而非为某一个具体问题硬编码答案。

TEST / HELD-OUT

留出测试集：验证泛化

优化器不应读它的具体题目和答案。每轮只读取必要的聚合测试指标，检验改动是否适用于未见数据。

最容易被忽略的一点：先估算 Eval 的随机波动。如果「可能的提升」比噪声还小，不该让 Agent 不停修改，而该增加样本量 / 重复次数或修复评分器。当连续 2–3 轮停滞时，先把失败按根因归类。

HOW TO RUN / CLAUDE CODE

原文给出的命令

先更新 Claude Code（原文称 claude-api skill 已内置），再在 Claude Code 的对话界面执行子命令；这些不是 PowerShell 系统命令。

claude update
/claude-api build-eval
/claude-api hillclimb

使用前应确定业务目标、项目入口、样本来源、成本预算和哪些文件允许改动。命令可用性取决于所安装的 Claude Code 与内置 Skill 版本。

REFERENCE PLAYBOOK / 可复制中文任务描述

让 Agent 按照这篇文章的方法工作

适用于你已有的 SDD → Implement → Review → Runtime Verification 流程中的评测阶段。

请先为当前 RAG / Agent 项目设计可靠的 Eval，不要立即修改代码。 1. 审视线上轨迹、Bug 和现有测试，从真实业务中抽样，并列出每题的来源、难度和预期结果。 2. 用确定性测试优先；开放问题用具体可核查断言及独立 LLM Judge。人工抽查评分结果。 3. 固定模型、参数、数据与运行环境，重复执行基线并估算评分方差与置信区间。 4. 随机分离 Train 和 Held-out Test：优化过程不可看到 Test 的具体输入与答案。 5. 每轮只提交一个可回滚 Patch，分别比较 Train/Test 指标、Token 成本和延迟；未超过噪声、不泛化或明显退化则回滚。 6. 连续停滞 2–3 轮时，暂停修改代码，对失败做根因分类，先修复有歧义的案例、错误评分与环境污染。 7. 最终提供 baseline vs best 的置信区间、逐例 Trace、改动 Diff、回滚依据与是否建议合并的结论。 先输出 Eval 设计方案并等待我确认评分规则和样本。

核心术语速查

Eval · 评测体系

可运行的测试样本、评分器、执行器与分析报告。

Grader · 评分器

检查输出是否达标的规则、程序或裁判模型。

Baseline · 基线

新改动之前、已固定配置下的初始性能。

Hillclimb · 爬山式优化

使用反馈信号反复提出小改动、验证、保留或回滚。

Held-out Test · 留出测试集

优化器不见题目的独立验证集，用来估计泛化。

Variance · 方差 / 波动

随机因素导致的得分不稳定；过大则难以验证小收益。
