01 / WHAT CHANGED

Code Mode 改变了什么？

Tool Calling（工具调用）解决“模型能调用哪些操作”；Code Mode（代码编排模式）进一步解决“哪些工具步骤无需每一步都让模型决策”。它是 Harness（Agent 执行框架）的调度策略，不是新的推理模型。

常规工具调用

模型决策→搜索→模型决策→读文件→模型决策→跑测试→模型总结

每次工具结果都可能触发一次新的模型调用，并携带已有上下文。

Code Mode

模型写执行计划→exec / JavaScript→搜索 + 读文件 + 测试→模型读结果

中间结果可在程序内部筛选与聚合，减少回到模型的频率。不代表零成本，也不代表所有步骤都能合并。

A

工具发现更精简

对模型暴露统一执行入口，减少大量工具 Schema 占用注意力与上下文。具体实现以 Harness 为准。

B

程序做确定性编排

循环、并发、过滤、去重、条件执行交给代码，而非每次调用后重新生成下一条 Tool Call。

C

减少重复上下文读取

模型少被唤醒一次，就少一次携带历史会话、工具输出与状态的请求；缓存命中也不等于零成本。

CONCEPTUAL EXAMPLE / 概念性示例

把三个可预测步骤合成一次执行

以下是接口无关的伪代码，用来说明控制流；实际工具名、权限和执行协议由所用 Harness 决定，并非可直接运行的 Pi 官方代码。

codemode · pseudo.js
// 由模型发起一次 exec，程序负责连续读取和裁剪
const hits = await tools.search({ query: "SSE disconnect" });
const paths = hits.slice(0, 8).map(x => x.path);
const files = await Promise.all(
  paths.map(path => tools.read({ path }))
);
const selected = files
  .filter(x => x.relevant)
  .map(x => ({ path: x.path, excerpt: x.excerpt }));
// 只把高价值证据交还给模型，由模型决策后续动作
return { inspected: paths.length, selected };
边界：不要把上面的概念性伪代码理解为“模型写的任意 JS 都可直接拥有所有工具权限”。生产实现仍需沙箱、工具白名单、结果大小限制、超时、审计与副作用隔离。

展开：这套模拟器怎么算的？

常规模型请求数 = 1 + 工具操作数；Code Mode 模型请求数 = 1 + ⌈工具操作数 ÷ 每次 exec 打包数⌉。累计重复输入 Token = 请求数 × 固定上下文 Token。折算输入费用 = 首轮全价输入 + (后续请求数 × 上下文 × [未命中比例 × 全价 + 命中比例 × 缓存价])。现实里还存在初始提示、输出 Token、上下文增长、缓存前缀失配、编排代码开销、工具返回与模型思考，因此只是用来建立直觉。

↳

怎么读模拟器：不是为了证明“打包数越大越好”。一个操作需要实时判断是否成功、是否越权、是否可以继续时，就不该为了省一次模型调用而盲目合并。

04 / CRITICAL THINKING

这是不是意味着 Pi 或 Code Mode 永远最便宜？

不。作者专门保留了实验局限。对比不同 Harness，需要同时看质量、任务分布、总费用、缓存、模型往返、执行时间，不能只看一个长任务的降幅。

更严谨的 A/B 实验，至少锁住这些变量

① 同基线 / 同任务 / 同模型

固定 Git commit、同样的任务与测试、相同模型版本和推理强度；不要让后续组享受前一组已经改好的代码。

② 每组多次运行 + 相同验收

统计 pass@1、测试通过率、真实浏览器验证、人工盲审；至少报告重复次数与离散程度。只比较最终截图不够。

③ 拆开计量，而不是只看 Total Tokens

单独记 input、cached input、output、模型请求数、tool call 数、执行时间、失败重试数与实际费用，才能定位改善来自哪里。

④ 检查副作用、回滚和错误恢复

Code Mode 合并步骤后，任何中间失败都可能影响剩余操作。需要知道在哪一步失败、哪些操作已经生效、是否允许安全重试。

适用边界：一两次简单工具调用、需要模型逐步看结果再决策、高风险写操作、可变的外部环境，Code Mode 可能没有优势，甚至可能增加调试和权限治理成本。
05 / DESIGN FOR YOUR AGENTS

如何应用到 RAG / DeepResearch / OnCall？

原文讨论编码 Agent；下面是针对应用型 Agent 的工程推导，不是作者验证过的性能收益。重点是 高频、可预测、只读 的步骤先组合，把决策和副作用留在受控边界。

适合部分组合信息获取 / 去重 / 裁剪

把机械检索打包，而不是把六个 Agent 合成一个黑盒

搜索 Agent 可以把「改写的多个 query → 批量搜索 → URL 去重 → 过滤低质量页 → 提取元信息 → Top-K」放在执行层。一轮返回紧凑 Evidence（证据）摘要；规划、证据冲突处理、结论修订仍交给模型。

  • 建议指标：LLM rounds / 查询、重复 URL 率、证据覆盖率、引用可溯源率、每份报告成本。
  • 必须保留：evidence_id → chunk_id → URL/时间戳映射，单次最多结果数，工具日志和失败重试标识。
  • 不要合并：需要语义复核的证据冲突、重要性判断、Replan（重规划）决策。
只读诊断优先修复动作单独授权

批量诊断很好；自动修复不能顺带执行

同一故障的日志、指标、最近部署、关联告警可以并行拉取后聚合到一个诊断对象；但任何重启、回滚、写数据库、变更配置都应经过权限检查和明确审批。

  • 建议指标：诊断时间、模型往返、Top-K 根因命中、误报率、自动动作审计完整率。
  • 必须保留：operation_id、幂等键、SOP 版本、告警指纹、权限与执行状态。
  • 不要合并：根因确认 → 生产修复之间的人工介入（HITL）或风险门禁。
适合确定性检索链不可牺牲召回

组合检索链很有用，但要防过早截断

向量检索、关键词检索、去重、过滤、Rerank（重排序）可在一个可观测执行单元中完成。只有最终候选的必要片段和引用元数据进入 LLM，减少中间结果反复进入上下文。

  • 建议指标：Recall@K、MRR/NDCG、正确引用率、单位查询成本、P95 延迟。
  • 必须保留：原始候选数、过滤原因、重排得分、chunk_id 与最终证据。
  • 不要合并：对于低置信或检索冲突的查询重规划；过早 Top-K 会伤召回。
✓

建议的实施顺序：先从只读、无副作用、能定量复现的检索链试点 → 接入模型请求与缓存计量 → 用线上回放样本 A/B → 过质量门槛后再灰度 → 最后考虑有副作用的操作。

07 / CHECK UNDERSTANDING

三道判断题：有没有真正理解？

不是考名词，考你在生产环境里会怎样做选择。每题选一个答案，会立即显示原因。

Q1. 一次 Agent 调用连续执行 12 次搜索/读取，耗费大量累计 Token。你应该先优化什么？

先测成本来自哪里，再控制跨模型往返。盲目删历史可能降低质量并破坏缓存；便宜模型也不保证任务总成本更低。

Q2. Code Mode 中已完成诊断，下一步要执行生产服务重启。最稳妥的做法？

节省模型往返不应跨越风险边界。生产写入要保留明确的决策、审批、审计与回放证据。

Q3. 单次实验显示费用降低 64%，这足以证明 Code Mode 总是更优吗？

单样本且基线发生变化，不能直接做强因果外推。成本下降需要与任务质量、稳定性、延迟共同评价。
